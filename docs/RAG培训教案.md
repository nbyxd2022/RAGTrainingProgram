# RAG 从零到能评测：按真实开发流程写的教案

> 用本仓库 `RAGTrainingProgram` 当教材。它不是"知识点串烧"，而是**一条问题链**：
> 每一步都是因为上一步撞了墙，才有下一个动作。教案里的每个数字都是我们自己跑出来的。
>
> - 语言/框架：Go 1.26 + [Eino](https://github.com/cloudwego/eino)（字节的 LLM 应用框架）
> - 模型服务：火山方舟 Ark（豆包 chat + doubao-embedding-vision 向量模型，2048 维）
> - 语料：17 篇中文公开文档，47.8 万字符（`corpus/`，清单见 `corpus/SOURCES.md`）
> - 代码量：约 2850 行 Go（8 个可执行工具 + 4 个内部包）
> - 全程只有检索与评测在本地跑，只有 embedding / chat 两次上网

### 0.4 一条主线（要看懂这五个词是怎么递进的）

```
能跑  → 跑得准  → 切得对  → 量得准  → 走向 Agent
阶段0/1   阶段2A    阶段2B    阶段2C     阶段3/4

**关键认知（整份教案的题眼）**：RAG 的每一次进步，都不是"换个更厉害的模型"，

## 1. 先把地图画出来

### 1.1 一个最小 RAG 就是四段流水线

```
用户问题 ──► ① 检索（在语料里找相关片段）──► ② 增强（把片段拼进提示词）──► ③ 生成（LLM 基于资料回答）
                     ▲
                  ④ 索引：离线把语料加载 → 切块 → 向量化 → 存起来（上面三步每问一次跑一次，这一步只跑一次）
```

**为什么要有它**：LLM 的知识冻结在训练数据里——不知道你公司的文档、不知道昨天发布的新闻。
RAG 不改变模型，只是在提问时**把相关资料塞进上下文**，让模型"看着资料答题"。

> 用我们语料里的话（`corpus/01-rag.md`）："RAG 通过在生成回答前引入信息检索环节来提升大语言模型的性能……
> 该方法有助于减少人工智能幻觉"。同一篇还给了反面案例：RAG 能防"没查到"，但防不了"查到了却理解错"。

### 1.2 为什么是 RAG，不是微调

| | 微调（Fine-tuning） | RAG |
| --- | --- | --- |
| 更新知识 | 要重新训练，贵 | 换一份语料，便宜 |
| 可溯源 | 说不清答案从哪来 | 每句能标"根据[1]" |
| 幻觉 | 仍可能编 | 资料里没有就能拒答 |

（`corpus/05-llm-intro.md` 1.2.2 节就在讲这两者的区别——我们后来把它做成了评测题 Q8。）

### 1.3 技术选型与理由

- **Eino**：Go 生态里少数的 LLM 应用框架，把 Loader / Transformer / Embedder / Retriever / ChatModel 都抽象成了接口。
  好处：我们**手写的每个部件都能挂进框架跑**（例如 `MemoryRetriever` 实现了 `retriever.Retriever`），
  以后想换成官方实现（如 Milvus 检索器）只需换一行构造代码。
- **火山方舟 Ark**：国内直连、有免费额度、chat 与 embedding 一个平台给全。
- **手写核心算法**：BM25、余弦、RRF、覆盖率都是自己写的，**不是为了省事，是为了学**——这些地方藏着 RAG 的全部"手感"。

## 2. 阶段 0：工程骨架（提交 51f4373）

### 2.1 先讲知识

三个概念，十分钟讲透：

1. **Embedding（向量化）**：把一段文字变成一串数字（本项目是 2048 个 float）。语义相近的文字，向量"方向"相近。
2. **Chat 模型**：输入消息列表、输出回答。它没有记忆、没有数据库，**只看得见你这次塞进去的上下文**。
3. **API Key**：既是钱袋子也是身份。**绝不能进 git**。

### 2.2 我们遇到的问题 → 方法

| 问题 | 症状 | 解决方法 | 代码位置 |
| --- | --- | --- | --- |
| 密钥怎么管 | 硬编码会被提交、会泄露 | `.env` + `godotenv`，`.gitignore` 排除；启动时检查缺哪个变量并明确报错 | `internal/config/config.go` |
| 不知道服务通不通 | 上来就写业务，报错分不清是网络、鉴权还是模型名错 | 先写**冒烟测试**：一次 embedding + 一次 chat，打印维度与 token 用量 | `cmd/smoke/main.go` |
| 语料从哪来 | 随便抓的文本质量差、有版权问题 | 17 篇公开文档（维基 CC BY-SA + Datawhale 教程），逐一登记来源与许可 | `corpus/SOURCES.md` |

### 2.3 一个真实的坑（值得单独讲）

方舟在售的向量模型是**多模态系列**（`doubao-embedding-vision-*`），必须走 `multi_modal_api` 端点，
默认端点会直接报错；而且**多模态接口一次只接受一条文本**，批量要自己切。

```go
// internal/llm/llm.go
apiType := arkembedding.APITypeMultiModal   // ← 不写这行就调不通
```

对应地，建索引时按 20 条一批提交，靠适配器内部的 5 路并发把吞吐提上去：

```go
// internal/rag/index.go
const batchSize = 20
```

## 3. 阶段 1：最小闭环（提交 f9e318b）

这一阶段的产物是一条能跑通的链：**加载 → 切块 → 向量化 → 内存检索 → 基于资料的生成**（`cmd/ask`）。

### 3.1 加载（Loader）

**问题**：语料是磁盘上的 `.md`，模型只认字符串。
**方法**：`LoadCorpus` 读目录下所有 `.md`（跳过 `SOURCES.md` 这种版权说明），每篇变成一个 `Document`。

**设计**：每个 `Document` 必须带 `ID`（文件名）和 `meta["source"]`（可回查的路径）。
——这不是洁癖：后面所有"回答里说 [1] 来源是某某文件"、"评测时把答案映射回原文"，
全靠这两个字段。**没有元数据的 RAG 是不可调试的 RAG。**

### 3.2 切块（Transformer）——学员动手 ①

**问题**：
1. 一篇文档几万字，不可能整篇塞进上下文（贵且模型会lost in the middle）；
2. 中文一个字占 3 个字节，**按 byte 切会切出乱码**。

**方法**：`SplitText(text, chunkSize, overlap)` —— 按 **rune（字符）** 切，定长 500、重叠 50：

```
块0: [0, 500)   块1: [450, 950)   块2: [900, 1400) ...   步长 = 500 - 50 = 450
```

**为什么要有重叠**：答案经常正好落在两个块的接缝上。重叠 50 个字符，等于给接缝加了一条安全带。
（这条安全带值多少钱？阶段 2B 量过：去掉重叠，BM25 的 cov@5 从 0.479 掉到 0.344。）

**设计**：切块时顺手把 `start / end`（这一块在原文里的 rune 区间）写进 meta。
——1.0 版本只是为了调试，到阶段 2B 才知道这是**跨切块策略比较的唯一桥梁**。
另外，块的 `ID` 是 `文件名#序号`（如 `01-rag.md#0`），三条检索路线才能按 ID 对齐、才能融合。

**动手**：`SplitText`（`internal/rag/splitter.go`）由学员实现，注意三个边界：
runes 不足一块、最后一块不满、`overlap >= chunkSize` 时直接返回空。

### 3.3 向量化（Embedder）

**问题**：1070 个块要逐条调用 API，慢且贵。
**方法**：
1. 批量提交（每批 20 条），
2. 向量存 `float32`（2048 维省一半磁盘，对排序没有影响），
3. **落盘成 `.gob`**（`VectorIndex.Save/Load`）——这是最省钱的一步：索引只建一次，
   之后所有实验（检索对比、评测）都读本地文件，**零 API 成本**。

**常见坑**：`idx.Entries` 里存的是"块原文 + 向量"，检索时不要就地修改 `MetaData`（会污染索引），
要复制一份再写 `score`——用户代码里那句注释"不能直接修改 entry.MetaData，这样会污染原数据"就是踩出来的。

### 3.4 检索（Retriever）——学员动手 ②

**问题**：给定问题，怎么在 1070 个向量里找最相关的？

**方法**：暴力检索 + 余弦相似度。**先别急着上向量数据库**——1070 个 2048 维向量，
单次查询是毫秒级，暴力算法在这种规模下完全够用，而且**全部代码可见、可断点、可对照**。
（向量数据库解决的是百万级 + 增删改 + 持久化，等撞到墙再上。）

余弦 = 两个向量夹角的余弦：`cos = a·b / (|a|·|b|)`。它只看**方向**不看长度，所以"长文本 vs 短问句"也能比。

**设计要点（两个"为什么"）**：
- 为什么要实现 Eino 接口：`var _ retriever.Retriever = (*MemoryRetriever)(nil)` ——
  用编译期断言把"我实现了这个接口"写进代码，接口变了立刻编译失败。
- 为什么用 `retriever.GetCommonOptions` 合并选项：让调用方能用 `WithTopK` 覆盖默认值，
  同时支持 `ScoreThreshold` 过滤低分结果（**这是防幻觉的第一道闸门**：分数太低 = 资料里可能根本没有）。

**动手**：`Cosine` 与 `MemoryRetriever.Retrieve`。推荐刻意练习：把 `Cosine` 写成 float64 累加
（float32 累 2048 项的误差没必要承担）。

**自检工具**：`cmd/sim` —— 三句话验证"同义靠近、异义远离"：

```go
// cmd/sim/main.go 里的三个句子
"检索增强生成（RAG）是一种让大模型先查资料再回答的技术。"
"RAG 通过检索外部知识库来减少大模型的幻觉。"      // 与第 1 句语义相关 → cos 应明显更高
"红烧肉的做法：五花肉切块，冷水下锅焯水，加冰糖炒出糖色。"  // 语义无关 → cos 应明显更低
```

**记住这组"刻度"（来自后续真实检索的实测）**：

| 场景 | 余弦分 |
| --- | --- |
| 真命中（答案块） | 0.68 ~ 0.79 |
| 噪声块（不相关的块） | 0.33 左右 |
| 同一语义换问法 | top-1 还是它，但分数从 0.79 掉到 0.54 |

**三个推论**（后面反复用到）：
1. 0.3 是噪声底——"最高分只有 0.33"时不要以为检索成功了；
2. 分数是**相对**的，**绝对阈值靠不住**（同一问题的前 4 名能挤在 0.4963~0.5073 的 1% 平局带里）；
3. 一条块的相关性并不可靠（尤其是 1070 块全量暴力检索时），所以下面要有"多路检索 + 融合"。

### 3.5 生成（ChatModel）——学员动手 ③

**问题**：检索回来了 3~5 段资料，怎么让模型"照着资料说"而不是自由发挥？

**方法**：提示词里写死三条纪律（`internal/rag/prompt.go` 的 `BuildMessages`）：

1. 只能依据给定资料回答；
2. 资料不足就明确说"资料里没有相关内容"，**不要编造**；
3. 引用资料要标编号和来源。

**设计细节（全是踩过的坑）**：
- 资料带编号 + 来源（`[1] 来源：corpus/01-rag.md`）：方便模型写"根据[1]"，也方便你事后核对。
- **不要把 `score` 放进提示词**：那是给工程用的元数据，对模型只是噪声。
- 资料和问题之间要有清晰边界（分隔线），别让模型分不清哪句是要回答的问题。

### 3.6 串链（compose.Chain）——一个值得讲的设计题

**问题**：用 Eino 的 `compose.Chain` 串"增强 → 生成"时发现：**问题丢了**。
链是单入单出的流水线，检索节点只能把 `[]*Document` 传给下一个节点，而拼提示词需要**问题和资料同时在场**。

**方法**：定义 `Retrieval{Question, Docs}` 这个结构体把它们一起往后传（`internal/rag/qa.go`）。

**更重要的追问**：那为什么不把检索也放进链里？
- 要在一个节点里汇合"两路数据"，得用 `compose.Graph` 的多路输入 —— 那是阶段 4 的内容；
- 检索结果在 `cmd/ask` 已经拿到并打印了（调试窗口），放进链里会**重复调用**，白付一次 embedding 的钱。

**设计心法**：框架是用来省重复劳动的，不是用来供奉的。**哪里放、哪里不放，标准是"调试可见性"和"钱包"。**

go run ./cmd/ask -q "什么是 RAG？" -k 5

## 4. 阶段 2A：混合检索 —— 一次失败案例引发的阶段（提交 1e05738）

### 4.1 触发问题（本阶段的全部动机）

学员先用阶段 1 的系统问了一句：**"BM25 是怎么工作的？"**

结果：向量检索 **top-3 全部落空**，最高分 0.3361——正好落在噪声带上（回忆 3.4 的锚点：噪声 0.3）。
但语料里明明有 BM25（`corpus/14-memory-retrieval.md` 发展历程一节）。

**根因**：向量检索擅长"意思像"，不擅长"字面像"。问题是术语，答案块里写的是 `TF-IDF`、`BM25` 这种缩写，
而文本里没有 BM25 这三个字母的语义邻居——**向量把"BM25"和"关键词匹配"之间的桥给塌了**。

**这就是"稀疏检索"存在的理由**：它不猜语义，只数"字面对上了几个词"，且会给稀有词更高的权重。

### 4.2 知识：BM25 是什么

对查询里的每个词条 `t`，在文档 `d` 上累加：

```
score(d) = Σ_t  IDF(t) · tf·(k1+1) / (tf + k1·(1 - b + b·len/avgdl))

IDF(t) = ln(1 + (N - df(t) + 0.5) / (df(t) + 0.5))
```

三个直觉（讲这三个就够，公式可以背不下来）：

| 符号 | 名字 | 它在干什么 |
| --- | --- | --- |
| `tf` | 词频 | 这个词在**这一块**里出现几次（出现越多越相关，但有饱和） |
| `df` | 文档频率 | 这个词在**多少块**里出现过（越稀罕越值钱 → IDF） |
| `k1` / `b` | 参数 | `k1=1.5` 控制词频饱和速度；`b=0.75` 惩罚长块（长块天生容易撞词） |

### 4.3 问题：中文没有空格，怎么分词？

英文可以按空格切，中文不行。我们选了**字符二元组（bigram）**：

```
"检索增强" → ["检索", "索增", "增强"]
"RAG 是什么" → ["ra", "ag", "是什", "什么"]   （先小写化，跨空白的词条丢掉）
```

**为什么不用分词器**：bigram 无需词典、不引入依赖、对术语与错别字鲁棒；
代价是"索增"这种无意义词条也会进索引——但对**查询和文档用同一套切法**时，字面命中依然可靠。
（这就是"工程上够用"的判断：先跑起来，撞墙再换 jieba/词级分词。）

**动手**：`Tokenize`（`internal/rag/tokenize.go`），注意两点：按 rune 不按 byte、跨空白跳过。

### 4.4 问题：两路分数根本没法比（0.68 vs 12.14）

向量分是 0~1 的余弦，BM25 分是无上界的正数（实测同一次查询里 BM25 冠军 12.14 分）。
**直接加权求和 = 用两把不同刻度的尺子量同一张桌子。**

**方法**：RRF（Reciprocal Rank Fusion）——**不比分数，只比名次**：

```
某条结果在某一路排第 r 名，就贡献 1/(k + r) 分，各路相加；k 惯例取 60。
```

名次天然归一化（第 1 名 1/61、第 2 名 1/62……），且**多路共识会被放大**：
一条结果被两路都命中，拿到两份分，自然排到前面。

**动手**：`FuseRRF`（`internal/rag/fuse.go`）。两个细节：并列时按 ID 升序兜底（**保证结果可复现**，对比实验才成立）；
排序要排自己的副本，别改传入的切片。

### 4.5 新问题：BM25 修好了它，又带来了三个新麻烦（实测）

| 麻烦 | 症状（真实数据） | 结论 / 对策方向 |
| --- | --- | --- |
| **IDF 悖论一：主题词不稀有** | "什么是 RAG？"里 `ra`/`ag` 的 df=464/446，idf≈0.85 → 正确的定义块 BM25 只排到第 80 | IDF 衡量的是"稀罕"不是"相关"；主题词在这个语料里到处都是 |
| **IDF 悖论二：最罕见 ≠ 最有信息量** | "幻觉太多怎么办？"的 BM25 冠军是 12-agent-intro#3=17.06 分，全部来自"怎么办？"（df=1，因为语料是书面"如何"风格），与"幻觉"零交集 | 提问措辞本身就是噪声；→ 停用词 / 查询改写（阶段 4） |
| **假共识（RRF 的盲区）** | "什么是 RAG？"里一个垃圾块（URL 列表，05-llm-intro#42）向量第 5 + BM25 第 6 → 融合后**升到第 2** | RRF 只放大名次共识、不辨内容；**修法在上游（数据清洗 / rerank），不在融合公式** |

**还有一笔"三重账"**（2A 评测数据，10 题，候选池 top-20）：

| 路线 | recall@5 | recall@10 | recall@20 | MRR |
| --- | --- | --- | --- | --- |
| 纯向量 | 0.683 | 0.883 | **1.000** | 0.704 |
| BM25 | 0.467 | 0.700 | 0.733 | 0.544 |
| RRF 融合 | **0.783** | 0.883 | 0.883 | 0.656 |

读出三件事：
1. **向量 R20 = 1.000**：10 题的答案**全都**在向量 top-20 里——问题不是"找不到"，是"埋在第 7~20 位排不上来"→ **rerank 的原料是充足的**；
2. **RRF 赢了 @5 输了 MRR**：融合把"两路共识"抬进前 5（Q7 0→0.5、Q8 0.5→1.0），
   但也会把"单路冠军"降位（Q1 0.25→0.14、Q2 1→0.33）；
3. **RRF 的 R20 = 0.883 < 向量**：融合榜把单路深部的条目挤出了前 20。
   → **设计教训：融合后的候选池必须取 union，别按融合榜砍 top-20。**

### 4.6 工程设计与工具

- **同一份块喂两条路线**：`idx.ToDocuments()` 把索引还原成块列表给 BM25 用；
  ID 一致 → RRF 才能按 ID 累计名次。代价是 BM25 每次启动重建（1070 块约 45ms），**不落盘**（省一份文件的心智负担）。
- **耗时结构**：向量 317ms（含网络）｜BM25 重建 45ms + 检索 <1ms｜RRF ~0。
- **工具**：`cmd/compare -q "..." [-k 5] [-n 20] [-idx .data/idx-heading.gob]`
  ——三路并排看排名、分数、耗时。**这是本项目的"显微镜"**，后面每个结论都是先用它看出来的。

## 5. 阶段 2B：切块策略 —— 从"块切得不好"到"怎么公平地量"（提交 7ed11db）

### 5.1 触发问题（两个标本）

| 标本 | 症状 | 根因 |
| --- | --- | --- |
| Q9"RAG 和微调有什么区别" | 一张 12 行对比表被定长切块切成**三块"半截表格"**，三路检索 @5 都只拿到 0.33 | 定长切块不认识 markdown 结构 |
| Q3 代码题 | 代码块被**拦腰截断**，且以代码开头的块匹配不上自然语言问句 | 同上：切块从段落/代码中间下手 |
| 通用 | 块的第一个字经常是半句话的中间 | 切块只按字符数，不看自然边界 |

**方法**：**结构感知切块**（`HeadingSplitter` / `SplitMarkdown`，`internal/rag/splitter.go`）：
按标题分节 → 节内按**自然单元**（段落 / 整个代码块 / 整张表）贪心打包到 ≤ maxLen，**不从单元内部切断**。

**实现要点（学员动手 ④）**：
1. **标题识别**要跟踪 ```` ``` ```` 代码围栏——语料里 Python/shell 注释全以 `#` 开头，
   不跟踪围栏会造出大量**假标题**；
2. **标题栈**：遇到更深的标题压栈、更浅/同级先弹再压，得到当前节点的标题链（`A > B > C`）；
3. **标题行本身不进正文**（标题信息由前缀表达），**节与节之间不重叠**；
4. **`start` 必须保真**：坐标一错，整个评测就崩（后面 2C 甚至加了体检来防这个）。

### 5.2 立刻撞上的新问题：换了切块，**指标本身失效了**

我们原来用 `recall@k`：看"前 k 条里有没有 gold 块"。
但**切块一变，块 ID 全变**（`01-rag.md#0` 在定长里和按标题里指的不是同一段文字），
而测试集的 gold 是用某一份索引的块 ID 标的 → **跨策略根本对不上**。

**方法**：换一把**与切块解耦的尺子** —— `coverage@k`：

```
coverage@k = |(前 k 条命中的区间并集) ∩ (gold 区间并集)| / |gold 区间并集|     （按 rune 字符数）
```

**为什么公平**：被度量的是"**答案文字带回来了多少**"，而不是"有没有命中某个特定块"。
无论怎么切，把答案那 300 个字带回来就是满分。

三个实现要点（学员动手 ⑤：`CoverageAtK`）：
1. 检索到的多条结果**先取并集再和 gold 求交**——直接逐条求交会把重叠部分（overlap 相邻块、多路命中）重复计数；
2. 按 `doc` 分组：不同文档的区间互不相干；
3. **漏召回的文档，长度留在分母里**（不然"少带一篇"反而变成高分）。

**还有一把辅助尺子"校正"**：按标题切块时，标题行不在任何块的正文区间里 →
gold 若跨过标题行，该策略**永远拿不到那几分**。于是算出每策略的"不可达区域"，
用 `校正 = cov × 并集 / 可达` 扣掉它。**（注意：这把尺子到 2C 就失效了，见 6.4。）**

### 5.3 结果：结构切块**没有赢**，但收益点和反作用力都找到了

旧尺子下的读数（cov@5/10/20，向量路）：

| 策略（块数） | cov@5 | cov@10 | cov@20 |
| --- | --- | --- | --- |
| 定长500/50（1070） | **0.691** | **0.888** | **1.000** |
| 定长500/0（964） | 0.693 | 0.857 | 0.929 |
| 按标题800（812） | 0.583 | 0.728 | 0.907 |
| 按标题500（1210） | 0.667 | 0.710 | 0.822 |

- **收益有证据**：Q9 表 0.36→0.67@5；Q4 三路 0.94（= 该策略可达上限）；Q8 向量 0.55→0.71@5。
- **反作用力 A · 面包屑撞词**：标题链前缀（`【第一章… > 1.2 什么是 RAG】`）拼进了每块正文 →
  **同一节的所有块共享同一段前缀** → 节内区分度下降；其他文档的标题词还会被 BM25 当正文命中
  （Q7 的 BM25 top 全是【习题】【…缩放法则与局限性】这类"局限性"字面块）。
- **反作用力 B · 整个代码块成了一个单元**：正文与代码分离后，**以代码开头的块匹配不上自然语言问句**（Q3 上限锁死 0.43）。
- **反作用力 C · gold 是按基线窗口标的**：跨自然边界时要多块同时命中（★ 这条到 2C 才被证伪为"尺子的锅"）。

### 5.4 消融实验：把面包屑移出正文（一次干净的单变量对照）

**设计**：只改一件事——标题链是拼进正文，还是只写进 `meta["heading_path"]`（`-strategy heading-nobc`）。切法、装箱、区间全不变。

**结果（配对差值，按标题800 → 无面包屑，向量路校正）**：
`@5 0.594 → 0.709（+0.115）`；`@10 0.741 → 0.785`；`@20 0.925 → 0.871（−0.054）`。

**结论：面包屑 = 用精排换召回**：
- **@5 涨**：同节块不再共享前缀 → 簇内区分度恢复。标本 Q1：定义块此前被同节 4 个带前缀的块挤到 rank 6，去掉前缀直接回到 @5（0.00→0.98）。
- **@10/@20 掉**：标题文字本来是"**免费的关键词锚点**"，去掉后整节召回变难。BM25 最明显（@20 0.762→0.631）。

**由此推出下一步的正解**（阶段 4）：**正文不带前缀保精排 + 命中后按 `heading_path` 把同节兄弟块聚合补回来** = Parent 策略。
**这就是"消融实验"的价值：它不只告诉你"哪个好"，它告诉你两个机制各自的代价，从而指出组合方案。**

### 5.5 一个方法论教训：全员零分，先查尺子

2A 时有一道题"如何评估 RAG 系统的效果？"三路全零。
第一反应是"检索太差"，诊断后发现：检索返回的块（08 章的评估相关块）**是合法的**，
是 **gold 标偏了**——问题问得太宽（"评估 RAG 系统的效果"整章都是答案）。

**改题**（收窄成"如何评估**检索**效果"，gold 换成 5.3.1 节）后三路满分。
**教训：检索指标全零时，第一件事是核对尺子，不是改检索。**

## 6. 阶段 2C：评测集定版 —— 尺子自己也有偏（提交 a46adb7）

### 6.1 触发问题：学员的一句质疑

> "gold 是按基准索引（500/50）的块 ID 标的吧？那 gold 区间不就是一个 **500 字窗口**吗？
> 窗口里混着标题行、代码注释、半句话；形状又恰好等于定长块的形状——
> **这不等于给'窗口形状'的策略发免费分吗？**"

**完全成立**。具体三宗罪：

1. **含非答案填充**：300 字的答案套在 500 字窗口里，定长块命中即 **1.0**，其中 200 字根本不是答案；
   而结构块老老实实交全答案只得 **0.8** —— 尺子在奖励"形状像窗口"的人。
2. **形状=窗口**：见上，"免费分"就是这么来的。
3. **绑死坐标系**：gold 是块 ID，只能在某一份索引上解读（重建索引 gold 就失效），且尺子和被测对象共享了同一套切块假设。

### 6.2 学员必问的两个问题（原样保留，讲课时直接用）

**Q1："那把 gold 按自然单元（章节）标，不就又和'按标题切块'彻底对齐了？换个方向偏袒？"**

A：**不存在零耦合的尺子**。尺子只能尽量少发免费分：
新尺子把 gold 收窄成"答成这样必须带上的那几句话"后，剩下的耦合只有一种——
**"固定切块会从答案文字中间切过"**，这是固定切块的真实代价，不是偏袒。
而且 gold 越小，这个代价的暴露面也越小。

**Q2："gold 只有几句话，那召回率不会虚高吗？（踩中一点就算对）"**

A：会**失去区分度**，但不会造假——这叫**天花板效应**。
实测坐实：新尺子下 21 题里，@5 只有 7 题能区分策略，其余 14 题五个策略全是 1.00。
对策不是把 gold 变大，而是**加题**（同义问法变体 / 多跳题）+ 用更细的指标（@1 排名敏感）。

### 6.3 方法：一整条工具链

设计方案（用户拍板的三件套）：

| 决定 | 内容 | 解决什么 |
| --- | --- | --- |
| **gold = 最小充分答案文本** | 一两句能答清就标那几句；表格/代码标整块；答案分散的题**标多段**（带回一段拿一段的分） | 杜绝"含填充"的免费分；多段压天花板 |
| **k 阶梯 @1/@3/@5/@10/@20** | `cov@1` 只看头名块——天然排名敏感，**取代单独的 MRR 列** | 区分"排第一"和"埋在第 5 位" |
| **汇总口径：macro 平均** | 每题先算值，再对题求平均 | 避免"gold 大的题"单方面支配总分 |

落地成一条**编译式标注工具链**（这是本阶段最值钱的工程成果）：

```
eval/testset.spec.txt        人读的标注源（===Q 问题 / tags: / note: / ===S 引文段）
        │  go run ./cmd/sections -emit eval/testset.spec.txt -out eval/testset.json
        ▼
eval/testset.json            机读产物：{question, tags, gold:[{doc,start,end,text}], note}
        │  cmd/eval 启动时：gold 体检（逐字比对语料切片）
        ▼
coverage@k 读数
```

三道保险：
1. **编译期**：每段引文必须与语料**逐字一致**，且**全语料恰好命中一次**——标错、标重直接报错（不是警告）；
2. **运行期**：`cmd/eval` 启动时做 **gold 体检**（`verifyGold`），拦住"语料被改过、标注没跟上"的漂移；
3. **自证**：JSON 里每段 gold 都带 `text` 原文，出问题可以直接肉眼比对。

**为什么值得这么麻烦**：标注是手工的、昂贵的、易错的；**尺子一旦不可信，后面所有实验全是废纸**。
把校验写成程序，是让"尺子"这件事从"人肉纪律"升级成"编译错误"。

### 6.4 回归读数（21 题 × 5 策略 × 3 路线，105 次 embedding 调用）

**向量路 cov@k**：

| 策略 | @1 | @3 | @5 | @10 | @20 |
| --- | --- | --- | --- | --- | --- |
| 定长500/50 | 0.502 | 0.764 | 0.892 | **0.965** | **0.965** |
| 定长500/0 | 0.385 | 0.786 | 0.838 | 0.944 | 0.952 |
| 按标题800 | 0.457 | 0.810 | 0.844 | 0.939 | **1.000** |
| 按标题500 | 0.439 | 0.840 | **0.918** | 0.918 | **1.000** |
| 按标题800无面包屑 | **0.552** | **0.857** | 0.857 | 0.905 | 0.939 |

**五条结论**：

1. **"定长最优"被削弱**：旧尺子下按标题800 落后定长 0.108，新尺子只落后 0.048；@5 上按标题500 反超 0.026
   ——**≈ 半道题，在噪声带内，不作超越宣称**。（差 0.026 为什么不能吹？21 题 → 1 题 = 0.0476，差值 < 0.10 基本是 2 题以内的事。）
2. **重叠 50 仍是净收益（复现）**：500/50 vs 500/0，向量 @5 0.892 vs 0.838。标本 Q9（gold 275 字跨块边界）：500/0 全 k = 0.00。
3. **Q14（Eino 代码题）成了新靶子**：@5 上按标题500 = 1.00、定长500/0 = 1.00，而定长500/50 = 0.47、按标题800 = 0.00
   ——同一个策略族里，**边界落在哪比策略叫什么更要紧**。
4. **"校正"列空转了**：21 题没有一题出现"可达 < 100%"。因为新 gold 已不含标题行，
   而标题行是结构策略唯一的不可达区域 → 校正 ≡ 原始。**列留着当探针**（将来若 gold 含标题、或某策略把正文挤出块区间，它会立刻报警）。
5. **区分度只集中在 7 题**（Q1/Q6/Q9/Q10/Q14/Q15/Q18）→ 下一版评测集要补同义问法变体、多跳题、更小 gold。

## 7. 阶段 3 / 4：接下来会发生什么（把 RAG 接入 Agent）

### 7.1 已知的坑位（都有实测证据支撑）

### 7.2 为什么这是通向 Agent 的路

本项目里已经出现 Agent 的三块砖：

1. **检索器 = 工具**：`MemoryRetriever` 已经是实现标准接口的"工具"，Agent 调工具和 RAG 检索是同一件事；
2. **评测 = 反馈信号**：Agent 的自我修正（Reflection）需要一个可度量的目标，那就是我们在 2C 建的东西；
3. **上下文工程**：提示词边界、编号引用、什么时候拒答——语料 `15-context-engineering.md` 整章在讲这些。

**下一步的自然延伸**：把"检索"从一个固定步骤，变成 Agent 可以**自主决定调几次、怎么改写查询**的动作

## 附录 B：Windows 命令速查（照抄即可）

```bat
go run ./cmd/smoke                                   :: 1. 验证密钥与网络
go run ./cmd/index                                   :: 2. 建默认索引（定长 500/50 → .data/vectors.gob）

go run ./cmd/eval                                     :: 6. 全量评测（5 策略 × 3 路线 × 21 题 = 105 次 embedding）
go run ./cmd/sections -emit eval/testset.spec.txt -out eval/testset.json   :: 7. 重编译评测集
```

**成本与耗时提示（讲给学员听）**：
- 建索引要调 API（1070 块约 1 分钟）；**索引落盘后所有实验都是本地的，零 API 成本**；
- 全量评测 105 次 embedding，向量检索本身不花钱；
- BM25 与评测计算全在本地 CPU 上，随便跑。

## 附录 C：踩坑速查表（症状 → 病因 → 药方）

| 症状 | 病因 | 药方 |
| --- | --- | --- |
| 中文变乱码 | 按 byte 切分 | 一律 `[]rune` |
| embedding 报错/404 | 多模态模型走了普通端点 | `APITypeMultiModal` |
| 回答没有出处、事后无法核对 | 元数据没带 `source/chunk_index/start/end` | `chunkMeta` 统一写入 |
| 模型自由发挥、编造 | 提示词没定边界 | 三条纪律 + "资料不足就直说" |
| 检索结果分数挤在一起（0.49~0.51） | 向量分数是"平局带"，阈值截断不可行 | 用 rerank 或相对比较，别用绝对阈值 |
| 融合后深部好块消失 | 按融合榜砍 top-20 | 池子取 **union** |
| 换个切块策略，评测数字全对不上 | gold 绑定了某索引的块 ID | gold 改**源文档字符区间** |
| 某题三路全零 | 可能不是检索的锅 | **先查 gold / 尺子**（Q10 的教训） |
| 结构切块"帮忙"了却仍输 | 面包屑撞词 / 代码块成整单元 | 做消融（单变量对照）再下结论 |
| 小数差 0.02 想宣布胜利 | 1 题 = 0.0476 的噪声 | 差值 < 0.10 不作超越宣称 |
| IDE 报红但编译通过 | gopls 缓存（本仓库常见） | 以 `go build` / `go vet` 为准 |

## 一页总结（给自己复盘用）

```
问题链（每一步都因上一步撞墙而起）：
  ① 模型不知道我们的文档              → 检索 + 增强 + 生成（阶段 1）
  ② "BM25 是怎么工作的"向量 top-3 全空 → 手写 bigram BM25 补字面（阶段 2A）
  ③ 两路分数不可比                    → RRF 按名次融合（阶段 2A）
  ④ 表格/代码/段落被切碎               → 结构感知切块（阶段 2B）
  ⑤ 换切块后 recall@k 对不上           → coverage@k 字符区间尺子（阶段 2B）
  ⑥ 面包屑既帮召回又伤精排             → 单变量消融 → 指向 Parent 聚合（阶段 2B）
  ⑦ 旧 gold 是 500 字窗口，给"窗口形状"发免费分 → 最小充分答案文本 + 编译式标注工具链（阶段 2C）

三条方法论（比任何公式都重要）：
  1. 先用显微镜看失败案例（cmd/compare / cmd/chunk），再谈优化；
  2. 换部件前先问"尺子会不会偏袒它"，再算噪声底，最后才读差值；
  3. 全员零分先查尺子——指标是代码的一部分，也是会坏的一部分。
```
